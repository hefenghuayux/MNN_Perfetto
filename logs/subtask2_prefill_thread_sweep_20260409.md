# 子任务2：Prefill 线程数扫描（当前可执行口径）

## 说明

原计划是固定绑核集合后，用 `-pt/-dt` 做 phase 独立线程扫描。实际执行时发现：

- 当前包 `work_steal_decode_blocks_current` 在 `prefill_threads < 4` 时会直接崩溃；
- 复现命令例如：
  - `-pt 2 -dt 2`
  - `-pt 2 -dt 5`
  - `-pt 3 -dt 6`
- 现象均为 `Segmentation fault`

因此，本子任务先采用“固定绑核集合 + 全局线程数扫描”的可执行口径，先把 Prefill 趋势测出来：

- 固定绑核：`2,3,4,5,6,7`
- 固定输入：`prompt=512`，`decode=128`
- 统计口径：`1` 次 warmup + `5` 次测量
- 运行方式：`-t 2..6 -ids 2,3,4,5,6,7 --split-phase-bench`

原始文件：

- `logs/subtask2_prefill_global_thread_sweep_raw_20260409.txt`
- `logs/subtask2_prefill_global_thread_sweep_20260409.tsv`

## Prefill 趋势结论

1. 在固定绑核 `2,3,4,5,6,7` 下，Prefill 性能随线程数增加持续改善。
2. 从 `2 -> 6` 线程，`pp512` 从 `1757.44 ms` 降到 `848.24 ms`，Prefill 吞吐从 `291.332 tok/s` 提升到 `603.603 tok/s`。
3. 当前这组点里，`6` 线程仍然是最优点，没有看到回落，说明当前 `work_steal` 版本下 Prefill 最优线程数至少不低于 `6`。
4. 因此，第4章里关于 Prefill 的结论可以先写成：
   - Prefill 对线程数更敏感；
   - 在当前平台和输入规模下，增加线程数能持续改善 Prefill；
   - 最优点明显高于 `4` 线程。

## 当前 blocker

### phase 独立线程扫描未完全打通

当前包对低 `prefill_threads` 的 phase 配置不稳定：

- `-pt 2` 崩溃
- `-pt 3` 崩溃
- `-pt 4/5/6` 可运行

这意味着：

1. 当前可以先用这张“固定绑核 + 全局线程数扫描表”支撑 Prefill 趋势。
2. 如果要严格完成论文里“Prefill phase 独立线程扫描”的版本，需要修掉 `-pt < 4` 的崩溃后重新打包再测。
3. 这个 blocker 不影响继续做后续不依赖 `-pt < 4` 的实验，但会影响“严格 phase 解耦”的线程扫描图。
