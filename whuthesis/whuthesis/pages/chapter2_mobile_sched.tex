\chapter{背景与动机}

\section{MNN 执行环境与移动端运行约束}

\subsection{移动端 CPU 推理的运行基础}

MNN 的 CPU 推理建立在后端抽象、并行执行框架和算子执行器之上。对调度优化而言，关键不在于单个算子内部做了什么，而在于阶段信息、线程数和绑核参数能否贯穿到整个执行过程。若不同阶段采用不同调度策略，就必须保证这些信息能够在运行时持续生效，而不是停留在应用层的局部配置中。

已有研究表明，通用推理框架如果忽略底层处理器异构性，很容易出现线程扩展性差和资源利用不均的问题\cite{wang2021asymo,xu2021coschedule,kang2020embedded}。这说明，调度信息必须进入框架运行路径，才能让优化真正作用于推理过程本身。

\subsection{Android/Linux 中的 affinity 与线程迁移}

移动端推理任务最终运行在 Android/Linux 调度器之上。即使没有 root 权限，用户态程序仍然可以通过标准 affinity 接口约束线程运行的 CPU 集合。这为分阶段绑核提供了基本条件，也决定了优化方案能够在普通开发环境下直接复现。

如果不显式设定 affinity，线程会由操作系统按全局负载自动分配。这样的默认策略对系统整体吞吐友好，但未必适合单个深度学习任务。推理线程在不同核心之间迁移后，缓存内容往往无法复用，局部性被打断，线程还可能落到性能较低的核心上继续执行。对于 Prefill 这类长任务阶段，迁移造成的性能损失会持续累积；对于 Decode 这类短步迭代阶段，迁移则会放大每一步的延迟抖动。

面向异构移动 CPU 的研究已经指出，线程分工与核心绑定必须结合考虑\cite{wang2021asymo,abdelgawad2022bertperf}。仅仅提高线程数并不能自动带来更好性能；若线程分布与核心能力不匹配，反而会加剧争用和拖尾。因此，affinity 与线程数是同等级的配置参数。

\subsection{无 root 条件下的 ADB 与 Perfetto 观测能力}

实验环境限定在无 root 条件下。这一约束会影响系统可观测性，但并不会妨碍调度研究的开展。通过 ADB 可以批量执行推理脚本、收集日志并控制实验流程；通过 Perfetto 仍然可以获得线程调度、CPU 运行时间片和部分系统事件轨迹。这些信息已经足以支持对“线程迁移是否减少”“高负载时是否出现尾部阻塞”“work stealing 是否缓解长尾”等问题的分析。

无 root 条件下，完整功耗信息和全部硬件计数器都难以方便获取。因此，实验评价不以能耗为核心目标，而集中在时延、吞吐、稳定性和调度行为四个方面。这样的取舍由实验边界决定，也更符合当前系统设计的实际条件。

\section{Prefill 与 Decode 的阶段差异}

\subsection{Prefill 阶段的长任务与负载不均}

在大语言模型推理中，Prefill 负责处理输入提示词并建立上下文状态。该阶段面对较长序列，单次执行包含更多算子调用和更大的张量规模。由于总工作量较大，整体吞吐和负载均衡成为主要问题。如果任务划分不均，尾部线程会显著拖慢整个阶段完成时间。

这一阶段与经典 work stealing 场景具有天然相似性：任务总体较大，局部不均衡会在运行过程中逐步暴露，而适度的任务窃取可以重新利用已经空闲的线程\cite{blumofe1999workstealing,acar2000locality}。但移动端推理并非一般意义上的对称并行程序，还受到异构核心能力差异和缓存局部性的约束。因此，窃取机制必须建立在较合理的初始任务组织之上，而不能完全依赖运行期竞争。

\subsection{Decode 阶段的短步迭代与同步开销}

Decode 阶段与 Prefill 有明显差异。此时模型按 token 逐步生成，单步任务规模更小，调用频率更高。系统不再追求一次性处理大量工作，而更关注每一步都尽量短、尽量稳。于是，核心问题从“如何提升总体负载均衡”转变为“如何避免调度本身成为额外负担”。

服务系统领域对 Prefill/Decode 差异的观察与这里的判断基本一致。Orca、PagedAttention、DistServe 和 Sarathi 等工作都指出，预填充和生成阶段的资源需求不同，若把它们视为完全同质的负载，系统性能往往会受限\cite{yu2022orca,kwon2023pagedattention,zhong2024distserve,agrawal2023sarathi}。虽然这些工作主要面向服务端，但其中关于阶段差异的结论同样适用于端侧。

因此，Decode 并不适合直接沿用 Prefill 的多队列窃取方式，而更适合采用轻量动态领取机制。原因很简单：单步任务过短时，复杂的窃取判定和多队列竞争反而会吃掉计算收益。

\subsection{阶段独立线程数和绑核的必要性}

一旦承认 Prefill 和 Decode 不是同一种负载，就必须进一步承认二者不应共用一套参数。Prefill 更看重大核利用和总吞吐；Decode 更看重执行稳定性和每步开销。前者通常可以接受更强的并行和更积极的 stealing，后者则更适合较轻的调度逻辑和更谨慎的线程扩展。

前期实验已经表明，两阶段性能曲线的最优线程数并不重合。相应地，两阶段的较优 CPU 集合也可能不同。对计算密集型阶段，可优先选取高性能核心；对更偏访存敏感、对尾延迟更敏感的阶段，则需要在性能和稳定性之间权衡。正因如此，阶段独立线程数和阶段独立 affinity 是方法设计的基本前提。

\section{现有任务划分与调度方法分析}

\subsection{静态划分、guided scheduling 与 work stealing}

静态划分的优点是简单、开销低、可预测性强。在线程能力相近、任务规模均匀的场景中，静态划分往往已经足够好。但在异构多核和运行时扰动明显的环境下，静态划分的弱点也很突出：一旦初始边界不合理，后续几乎没有自我修正能力。

guided scheduling 在此基础上引入了逐步缩小任务块的思想。其核心目的是在保留较低调度开销的同时减轻尾部不均衡\cite{polychronopoulos1987guided}。这一思想对调度设计有启发，但 Prefill 面临的并不是抽象对称处理器，而是异构多核和高负载扰动。相比之下，work stealing 更适合处理“初始分工大体合理，但运行过程中仍可能出现局部失衡”的场景\cite{blumofe1999workstealing,frigo1998cilk5}。

work stealing 的经典设计是每个工作线程维护本地双端队列，线程优先从本地队列取任务；当本地队列为空时，再去窃取其他线程队列头部或尾部的任务。Chase-Lev deque 以及针对弱内存模型的后续工作，进一步给出了这种结构在无锁并发环境中的工程实现方式\cite{chase2005deque,le2013weakmemory}。这为 ARM 平台上的无锁任务窃取提供了直接参考。

\subsection{异构多核上的性能比建模与加权划分}

异构多核任务划分不能只回答“划多少”，还要回答“按什么比例划”。移动端推理相关研究已经反复说明，异构处理器上的一个常见误区，就是把不同核心当作同构资源使用\cite{wang2021asymo,liu2024pitfalls}。若忽略核心能力差异，线程扩展性会迅速恶化；若只使用固定经验值，又可能在不同模型和不同机型上失准。

AsyMo 等工作给出的启示是：异构调度应尽可能建立在目标负载和目标硬件的可测特征上，而不是完全依赖通用经验参数\cite{wang2021asymo}。BERTPerf 则说明，big.LITTLE 上的推理延迟与配置参数之间存在复杂关系，必须通过建模或实测加以刻画\cite{abdelgawad2022bertperf}。这些结论共同说明，真实能力测量比统一经验参数更可靠。

顺着这一思路，核心性能比标定便成为初始任务组织之前的重要步骤。它并不追求复杂的全局最优模型，而是服务于一个更直接的目标：让初始任务边界尽量符合目标机型的真实速度关系。后续的 work stealing 则负责处理仍然存在的残余失衡。

\subsection{移动端推理框架中的已有不足}

现有框架和相关工作中，移动端推理优化主要集中在算子实现、量化、异构协同和调度建模几个方向\cite{jia2022codl,xu2021coschedule,niu2024smartmem}。这些研究提供了大量有价值的经验，但围绕“无 root、本地可运行、直接落到 MNN”这一目标，仍然存在三个缺口。

第一，很多优化建立在通用异构协同或特定硬件后端上，未必直接适配只使用 CPU 的端侧部署路径。第二，许多研究强调离线建模和全局计划，但对高负载干扰下的运行时纠偏讨论仍不充分。第三，面向大模型推理时，Prefill 与 Decode 的阶段差异已被服务系统研究充分关注，却较少被直接映射到移动端 CPU 后端调度中。

\section{问题归纳与设计目标}

\subsection{设计目标}

结合前述分析，优化目标集中在三个方面。其一，在无 root 条件下提升端侧推理性能，缩短 Prefill 和 Decode 的执行时间。其二，在背景负载存在时保持较好的稳定性，减少长尾和明显抖动。其三，在保持实现简洁的前提下，将调度逻辑嵌入现有推理执行路径，使方案具备可复现性和工程可用性。

\subsection{约束条件}

方法设计并不试图控制整个系统调度器，也不依赖特权接口读取功耗或修改 governor。优化必须在普通用户权限下完成，能够通过应用层或用户态运行时直接生效。同时，也不宜对 MNN 做大规模结构重写，而应尽量利用现有执行路径完成最小侵入式改造。

\subsection{评价指标}

基于上述目标和约束，后续实验重点关注以下指标：Prefill 阶段吞吐、Decode 阶段吞吐、首 token 时延、端到端时延、重复实验下的稳定性统计，以及基于日志和 Perfetto 的线程调度行为指标。对于 work stealing，还需要额外记录窃取尝试次数、窃取成功次数和被窃取任务量等统计量，以便把性能变化与调度行为直接对应起来。
